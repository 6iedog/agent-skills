# 通用组件设计契约

> 与具体组件库无关。项目用 antd、Element Plus、shadcn 还是自研，这套契约都成立。
> 参考对象是成熟组件库的**文档信息组织方式**——它的价值在于"一个组件该被描述清楚哪些维度"，而不是它有哪些组件。

## 为什么需要契约

用户说「做个下拉选择框」，AI 立刻开始写代码。写完发现用户要的是能搜索的那种——**因为「下拉选择框」这个词不携带足够信息**。

组件设计契约的作用是：**把一个模糊的需求，展开成必须回答清楚的问题清单**。清单里的问题来自组件本身的结构，不来自某个库的 API。

## 契约的七个维度

任何组件——不管是库里的还是自研的——都应能按这七维描述清楚。缺哪一维，AI 就只能靠猜。

```
1. 角色      这个组件解决什么问题        → 决定了「什么时候不该用它」
2. 数据契约  输入什么形状、什么量级      → 决定了形态分支（单选/多选/层级/搜索）
3. 交互契约  用户怎么操作、系统怎么响应   → 决定了「状态如何流转」
4. 状态全枚举 所有状态组合              → 决定了「会不会漏状态」
5. 边界与代价 做不到什么、代价是什么     → 决定了「会不会造出烂体验」
6. 变体轴    哪些维度可配               → 决定了「能不能复用而不是复制」
7. 无障碍    键盘、焦点、读屏            → 决定了「能不能用」
```

### 1. 角色

一句话说清它解决什么问题，以及**不解决什么**。

不写「不解决什么」，AI 会在不该用它的时候用它——这是最常见的组件误用来源。

```
✓ 日期选择器：让用户按日历选择日期。不处理时区转换，
  不处理「只有年没有月」的场景（那是 RangePicker 的退化用法）。
✗ 日期选择器：用来选日期。
```

### 2. 数据契约

**这一维决定了形态分支，是消歧的主战场。**

必答四问：

| 问 | 为什么 |
|---|---|
| **数据形状** | 扁平列表 / 有层级 / 任意深度树 / 键值对 |
| **数据量级** | 决定要不要搜索、分页、虚拟滚动 |
| **可否自造** | 允许用户输入列表外的值吗（会污染数据） |
| **变更频率** | 静态枚举还是频繁变化（决定要不要远程搜索） |

**量级是关键**。同一形态在 20 条和 5000 条时是两种组件：20 条用下拉合理，5000 条必须能搜索+虚拟滚动。不问量级，AI 大概率按前者做，用户滚死在列表里。

### 3. 交互契约

用户动作 → 系统响应，逐步写清：

```
用户点开 → 展示什么（选项列表 / 树 / 分组）
用户筛选 → 匹配哪些字段（名称？编码？名称+编码？）
用户选择 → 怎么回填（显示 label 还是 id？已选项是否折叠？）
用户反悔 → 能否清除？清除后回到什么状态？
用户取消 → 状态是否保留（下次打开是空的还是保留上次的）
```

**「用户反悔」和「用户取消」最容易漏**，而这两个恰恰是体验投诉的重灾区。

### 4. 状态全枚举

任何组件的规格文档必须覆盖这 12 个状态，逐条写视觉与行为：

```
default      默认
hover        悬停（触屏无此态，平台差异）
focus        聚焦（键盘导航触发）
active       按下
selected     选中
disabled     禁用 —— 附原因说明
readonly     只读 —— 与 disabled 的区别必须写清
loading      加载中 —— 是否阻塞交互
error        错误 —— 附错误文案口径
empty        空 —— 区分「首次为空」与「筛选后为空」
```

**disabled 与 readonly 必须分开定义**：
- `disabled` 不可交互，通常置灰
- `readonly` 不可编辑但内容可读可复制，**视觉上不应置灰**

表单里混用两者是常见错误——用户看到置灰的字段以为是坏的，其实只是不能改。

**empty 必须区分两种**：
- 首次为空 → 引导创建（「还没有订单，去创建」）
- 筛选后为空 → 引导清除筛选（「没有符合条件的结果，清除筛选」）

同一个「暂无数据」用在这两种场景，是把两个不同的问题混成一个。

### 5. 边界与代价

**这一维最容易被跳过，也最影响最终体验。**

必答：
- 数量上限是多少？超出会怎样？
- 数据为空会怎样？加载失败会怎样？
- 用户做了不该做的操作会怎样（禁用的项被强行提交）？
- 有没有**看起来能用但实际会崩**的组合？

「边界与代价」的写法：

```
✓ 多选超过 20 个标签会把控件撑爆 → 必须设上限 + 标签收纳
✓ 选项超过 100 条渲染会卡顿 → 必须虚拟滚动或改为搜索
✓ 表单弹窗关闭后内部状态不保留 → 需要 preserve 或 clear 处理

✗ 多选支持多个
✗ 支持大数据量
```

**「支持 X」不是边界，「X 到 Y 程度时会 Z」才是边界。**

### 6. 变体轴

组件在哪些维度上可配。列清楚才能**复用而不是复制**。

```
size:     compact / default / large
variant:  outlined / filled / borderless
state:    default / hover / disabled / loading / error
```

如果两个组件的变体轴完全一致，它们**应该合并**。如果某个变体只有一个组件在用，说明它可能是过度设计。

### 7. 无障碍

- Tab 顺序是否符合视觉顺序？
- 焦点是否可见？（不能用 `:focus` 代替 `:focus-visible`，鼠标点击也会触发焦点环）
- 弹层打开时焦点去哪、关闭时回到哪？
- 图标按钮有无障碍名称？
- 能否纯键盘完成操作？

**无障碍不是加分项**。读屏用户和纯键盘用户是真实用户，只是占比低。

## 契约怎么用

### 生成组件时

按七维顺序展开，**每维填不满就是信息缺口**，缺口要么从代码推断，要么问用户。

生成前必须回答的前三问（缺了就会做错）：

```
1. 数据量级多少？          → 决定形态分支
2. 用户反悔/取消会怎样？    → 决定状态流转
3. 有什么做不到的？         → 决定要不要警告用户
```

### 审查组件时

拿七维当检查清单，逐维打分：

- 角色 —— 说得清不解决什么吗？
- 数据契约 —— 量级与形状明确吗？
- 交互契约 —— 反悔路径写了嗎？
- 状态 —— 12 个状态齐吗？disabled/readonly 分开了吗？
- 边界 —— 有「到 Y 程度会 Z」的表述吗？
- 变体轴 —— 与其他组件是否重复？
- 无障碍 —— 键盘能走通吗？

### 判断该不该新建组件

**变体轴是最好的判据**。新建之前问：

```
这个新组件的变体轴，和已有组件重合吗？
  重合高 → 扩展已有组件（加 variant / prop），不新建
  重合低 → 才考虑新建

新建后，它的每个变体都有真实使用场景吗？
  没有 → 过度设计，等需要时再加
```

## 契约与「组件库」的关系

这套契约**不关心**组件从哪来：

| 组件来源 | 契约怎么用 |
|---|---|
| 用现成库组件 | 读库文档，按七维补齐它没说清的部分（如「什么时候不该用」） |
| 组合库组件 | 契约写在包装层，注明组合了哪些库组件及其代价 |
| 自研组件 | 七维全部由你定义，这是自研的主要成本 |
| 包装库组件补能力 | 库组件缺什么（如缺空状态引导）→ 包装层补，但要在契约里记明 |

**库组件的文档通常只覆盖数据契约和变体轴**（因为那是 API 列表），而**角色、边界、无障碍这三维常常缺失**——需要你补，这正是它不够好用的原因。

## 契约的信息来源优先级

写契约时按此顺序取证，不要凭印象：

```
1. 项目已有同类组件的实现     ← 最强信号，直接照抄
2. 项目 conventions.md 的既有约定
3. 设计系统文档 / 团队规范
4. 组件库官方文档            ← 只能覆盖 API 层面
5. 通用工程经验              ← 最后兜底，且要标注"需确认"
```

**第 5 条要特别警惕**。凭印象写「弹层默认要挂 body」这类结论，如果与项目实际不符，会稳定地产出错误组件。宁可留空等用户确认。

## 清单

新增或审查组件时逐条过：

- [ ] 角色写清了**不解决什么**
- [ ] 数据契约四问都答了（形状/量级/可否自造/变更频率）
- [ ] 交互契约覆盖了**反悔与取消**
- [ ] 12 个状态齐全，disabled 与 readonly 分开
- [ ] 空状态区分了「首次」与「筛选后」
- [ ] 边界写成「到 Y 程度会 Z」，不是「支持 X」
- [ ] 变体轴与其他组件比对过，没有重复
- [ ] 键盘可完整操作，焦点可见
- [ ] 所有数值来自设计令牌，无硬编码
- [ ] 每条规则标注了来源（代码/规范/库文档/待确认）
