# 样式体系：探明位置 + 写一份 wiki

核心：**样式值不该有第二份定义**。值从哪来、填完谁维护都是死结。解法不是写更多解析器，而是**不做中间层**。

## 1 不要写解析器、不要做中间层

模型能读任何格式的样式文件，它需要的是**知道去哪读**，不是让工具替它读。

- CSS 变量、Tailwind 配置、SCSS / LESS 变量、主题对象、组件库主题——直接读文件即可理解，不需要为每种格式写 parser。
- 抽出来的值就是漂移的来源。

## 2 探索一次，产出「样式 wiki」

初始化时探索一遍，产出一份**描述性文档**，写进**组件创建提示词**。

| wiki 写什么 | 例 |
|---|---|
| 样式定义在哪些文件 | `src/styles/theme.css`、`tailwind.config.js` |
| 用了什么机制 | CSS 变量 / Tailwind / SCSS / 主题对象 / 组件库主题 |
| 关键约定 | 命名规范、分层方式、**新增一个值该怎么加** |
| 变体与状态怎么表达 | 如 `--btn-primary-hover` 这种派生命名 |
| 已知例外与历史包袱 | 哪些地方没遵守（避免模型以为要照抄） |

**wiki 是地图，不是副本**：写「主色定义在 `theme.css` 的 `--brand-primary`」，**不复制 `#1677ff`**。

**新增值必须落到样式源**：样式源里没有的值（如缺「危险色」），要按「新增一个值」的流程**加进样式源**，不得用组件库内置调色板 / 框架默认值顶替——那等于第二份定义。

写一次就够。样式调整时 wiki 通常不用改（位置没变）；真变了，模型读文件时自然会看到。

## 3 没有统一样式的项目（常态，不是例外）

此时任务是**建立统一**，不是「适配已有的」：

```
1 用搜索统计重复出现的值（普通搜索命令即可，不需要专用扫描器）
   → 用了 30 次的那个蓝色，大概率就是主色
   → 圆角只有 6px / 12px 两个值在反复出现
2 提出一套最小令牌集，附「出现次数 / 出处」作依据
3 用户确认后写入项目
4 更新样式 wiki，记录这次的约定
```

**关键是从现状归纳，不是从零发明。** 用户看到「这个蓝色在你代码里出现 30 次」才会认可它是主色；凭空给个 `#1677ff` 没人认。

统计只做**这一次**。之后不再重复提取值。

## 4 检查：找出来 ≠ 下判断

```
第一步 找出所有硬编码值   →  普通搜索即可
        输出：位置 + 值 + 出现次数
第二步 判断是不是问题     →  模型做
        依据：它读了样式源，知道哪些值有出处
```

第一步不需要专用工具（搜索更透明、可现场调整）；第二步不能交给工具（「这个 13px 有没有依据」要看它对不对得上样式源的定义，需要理解，正则判不了）。

**不要做成「脚本报错就阻断」的硬门禁。** 检测不到样式体系时更不该报错，而应列出全部硬编码值及频次——这份输出正好是第 3 节归纳的输入。
