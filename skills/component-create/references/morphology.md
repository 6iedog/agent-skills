# 形态消歧

## 这一层解决什么

用户说「做个下拉选择框」，这句话里混了两种东西：

```
「下拉选择框」
   │      └── 形态词（下拉）：只是视觉形态，不含任何数据信息
   └───────── 语义词（选择）：范围极宽，业界有 9 种以上形态
```

**「选择」具体指哪一种，取决于用户的数据，不取决于这个词。**

### 不消歧的真实代价

需求是「从 500 个商品里搜一个」，做成普通下拉框：

- 组件层面**完全符合要求** —— 确实是下拉、确实是单选、确实能选
- 体验层面是灾难 —— 用户要滚动 500 项

**这类错误不报错、代码评审看不出来、测试也测不出，但用户立刻感受到。**

反例同样存在：需求是「选 3 个标签」，做成单选下拉，用户发现选不了第二个，只能回来改。

## 关键认知：不要问「你要哪种形态」

这是最容易犯的错。列出所有形态让用户选，等于把问题原样退回：

```
✗ 「你要哪种下拉？单选 / 多选 / 搜索 / 标签 / 级联 / 树形 / 按钮组 / 分段 / 穿梭框」
   → 用户不知道「级联」是什么，也不知道自己的需求对应哪个
```

**正确做法：问数据特征。** 每个形态都对应一组明确的数据条件，条件问对了，形态自然确定。

```
✓ 「数据有层级关系吗？」        → 有 → 级联或树形
✓ 「大概多少条？」              → 20 内 → 简单选择；20+ → 需要搜索
✓ 「需要同时选多个吗？」        → 是 → 多选（追问上限）
```

用户不知道什么叫级联，但一定知道自己的数据有没有层级。

## 消歧顺序：先读，再二分，最后才问

```
1. 读数据源   → 接口返回什么结构？多少条？可否自造？   ← 最强信号
2. 读已有代码 → 项目里同类场景怎么做的？（registry.json）
3. 二分提问   → 用数据特征问，一次问一个
4. 明确询问   → 前三者都定不了，且选错会返工
```

**大多数情况在第 1 步就结束了。** 用户描述不清楚，但数据是清楚的——先读数据，别急着问人。

## 形态判定表

形态由数据条件决定，不需要先知道组件库有什么。

### 选择类

| 形态 | 判定条件 | 实现方向 |
|---|---|---|
| **单选** | 单层 + 少量（< 20）+ 不需搜索 | 下拉或按钮组（≤ 5 时） |
| **搜索单选** | 单层 + 大量（≥ 20）或用户按名查找 | 可输入的下拉 + 过滤 |
| **多选** | 需同时选多个 + 数量有限 | 多选 + **必须设上限** |
| **标签输入** | 多选 + 允许自造列表外的值 | 可输入的多选 |
| **级联选择** | 层级明确且深度固定（如省市区） | 逐级选择 |
| **树形选择** | 层级深且不固定（组织架构、目录） | 树形 |
| **按钮组** | 选项 ≤ 5 且要一屏看全 | 横向按钮 |
| **分段控件** | 2-4 个互斥**视图切换**（非数据选择） | 分段 |
| **穿梭框** | 从大量条目中挑少量到目标列表 | 双栏穿梭 |

**判定顺序**（命中即停）：

```
1. 数据有层级吗？        → 有 → 深度固定？级联 : 树形
2. 单层 → 2. 多少条？   → ≥20 → 3. : 单选（≤5 考虑按钮组）
3. 需多选吗？            → 是 → 4.
4. 允许自造吗？          → 是 → 标签输入 : 多选（追问上限）
5. 是数据选择还是视图切换？ → 视图切换 → 分段控件
```

### 弹层类

| 形态 | 判定条件 | 注意 |
|---|---|---|
| **Modal** | 需要中断当前操作去完成另一件事 | 简单确认用轻量的 |
| **Drawer** | 内容较长，需边看边参考背景 | 内容短时 Modal 更聚焦 |
| **Popconfirm** | 轻量确认，可就地完成 | 文案长会被截断 |
| **Popover** | 补充说明且**需要交互** | 纯文字用 Tooltip |
| **Tooltip** | 纯文字补充 | **不能承载可点击内容** |

**判定**：

```
1. 只是在确认，还是要在里面做操作？ → 确认 → 2. : Modal / Drawer
2. 影响面小可就地完成？            → 是 → Popconfirm : Modal
3. 内容多不多？                    → 多 → Drawer : Modal
4. 能点里面的东西吗？              → 能 → Popover : 不能 → Tooltip
```

### 数据展示类

| 形态 | 判定条件 |
|---|---|
| **Table** | 字段固定成列，需排序/筛选/对齐比较 |
| **List** | 结构不固定，或卡片式，或需配图 |
| **Tree / Tree Table** | 层级数据 |

**判定**：

```
1. 字段是固定的几列吗？ → 是 → 2. : List
2. 有层级吗？            → 有 → 层级展示形态
3. 多少行？              → 上百 → 分页或虚拟滚动
```

### 输入类

| 形态 | 判定条件 |
|---|---|
| **单行** | 短文本 |
| **多行** | 长文本或需换行 |
| **数字输入** | 纯数字且需增减 |
| **日期/时间** | 日期时间（注意粒度：只到年？年月？日？） |
| **范围选择** | 起止区间 |

**最易漏的是输入约束**：最大长度、允许字符、是否允许粘贴、精度。以及**输入过程中不要报错**，改为失焦校验。

### 反馈类

| 形态 | 判定条件 |
|---|---|
| **Toast** | 操作已完成，无需后续动作 |
| **Alert** | 页面级持续提示 |
| **Modal** | 已发生且不可自动恢复的错误 |
| **骨架屏** | 1-10s 的区域加载 |
| **全屏遮罩** | 阻断性操作（不该用于局部加载） |

**判定**：

```
1. 用户需要做点什么吗？ → 是 → Modal : Toast
2. 大概多久？           → <1s → spinner；1-10s → 骨架屏
3. 需要阻断用户吗？     → 否 → 局部 : 是 → 全屏
```

### 形态词 → 语义族

听到这些词时，先归到族，再进判定表：

| 形态词 | 语义族 |
|---|---|
| 下拉、下拉框、选择框、picker、选择器 | 选择类 |
| 输入框、输入、填一下、text | 输入类 |
| 弹窗、对话框、modal、遮罩、抽屉、drawer | 弹层类 |
| 表格、列表、table、list | 数据展示类 |
| 标签、tag、徽标、页签、tab、菜单、导航 | 标签导航类 |
| 提示、气泡、tooltip、popover | 叠加提示类 |
| 加载、loading、Spinner、骨架、进度 | 反馈类 |
| 折叠、面板、手风琴、分隔 | 布局类 |

**注意**：用户几乎总是在描述**视觉形态**（下拉、弹窗、抽屉），而真正决定形态的是**数据特征**。听到形态词，第一反应应该是问数据，不是去找那个视觉形态的组件。

## 用户指定了形态或组件时

即使用户已经指定，仍要检查边界——**指定的人常常只知道名字，不知道它做不到什么**。

```
用户：用下拉做多选，选了 30 项
  → 检查：多选的边界是什么？30 个标签会撑爆控件
  → 说明代价 + 给方案（设上限收纳 / 换穿梭框）
```

**说清代价让用户决定**，不要只说「不建议」。

## 记录消歧结论

消歧结果要写进组件规格，否则下次重新走一遍：

```json
{
  "morphology": {
    "requested": "下拉选择框",
    "resolved": "可搜索的单选下拉",
    "reason": "商品约 800 条，普通下拉需长距离滚动",
    "data_shape": "扁平数组，无层级，单选",
    "alternatives_considered": [
      { "option": "穿梭框", "rejected": "目标列表只选 1-3 个，占屏太大" },
      { "option": "标签输入", "rejected": "不允许自造商品 id，会污染数据" }
    ],
    "implementation_note": "基于项目的 Select 组件，加 showSearch 能力"
  }
}
```

**记录要写通用描述（「可搜索的单选下拉」），不要只写组件名** —— 组件名会随库升级或换库而失效，形态描述不会。

写入 `.ui-kit/catalog/<Component>.md` 第 1 节 + `logs/decisions.mdl`。

**晋升机制**：同类需求出现 2 次以上相同结论（如「商品选择一律用可搜索下拉」），写入 `conventions.md`，下次直接采用**不必重新消歧**。

## 完整示例

### 输入

> 「订单页要加个下拉选择框选商品」

### 步骤

```
1. 读数据源：/api/products 返回扁平数组，约 800 条，无 parentId
   → 扁平无层级 → 排除级联、树形
   → 800 条 → 排除简单下拉（无法承载）
   → 方向收敛：可搜索的单选下拉
2. 读已有代码：项目内无同类先例
3. 判定完成，零提问
```

**此处在数据层就完成了消歧，用户一个问题都没答。**

### 只剩一个真问题

```
搜索时只匹配商品名称，还是也要匹配编码？
影响：决定过滤时匹配哪些字段，后端是否要改
```

### 复述给用户

> 订单页的商品选择：约 800 条商品、无层级关系，用**可搜索的单选下拉**。
> 排除了级联/树形（数据无层级）、穿梭框（只选 1-3 个，占屏太大）、标签输入（会允许提交不存在的商品 id）。
> 搜索匹配哪些字段还需你确认。

**这段话做了三件事**：给结论、说排除理由、指出唯一待确认项。用户不需要懂组件也能判断对不对。

## 常见误用速查

| 目标 | 容易误选 | 实际应该 | 判据 |
|---|---|---|---|
| 从很多里选一个 | 简单下拉 | 可搜索下拉 | 量级 ≥ 20 |
| 选 2-3 项 | 多选无上限 | 多选 + 上限收纳 | 无上限会撑爆 |
| 选省市区 | 下拉 + 自己拼层级 | 级联/树形 | 数据有层级 |
| 选一个但要能搜能新造 | 单选下拉 | 可输入的选择 | 允许自造 |
| 筛选项只有 3 个 | 下拉 | 按钮组 | ≤ 5 且要一屏看全 |
| 切换三个视图 | 下拉 | 分段控件 | 视图切换非数据选择 |
| 确认删除一条 | 弹窗 | 轻量确认 | 影响面小，可就地完成 |
| 表格里改一个字段 | 弹窗编辑 | 行内编辑 | 高频操作弹窗太重 |
| 加载列表 3 秒 | 全屏遮罩 | 骨架屏 | 不该阻断用户 |
| 从 500 条里挑 5 个 | 穿梭框 | 多选 + 搜索 | 目标少时穿梭框占屏太大 |

## 反模式

| 反模式 | 问题 | 正确做法 |
|---|---|---|
| 直接找"下拉框"就开始写 | 500 条数据做成简单下拉 | 先读数据量级 |
| 罗列所有形态让用户选 | 用户不懂这些术语 | 问数据特征 |
| 问细节之前不定形态 | 组件可能根本不需要弹层 | 顺序：先形态，后细节 |
| 形态结论只写组件名 | 换库或升级即失效 | 写通用形态描述 |
| 用户指定就跳过检查 | 指定的人常不知组件边界 | 说明代价让用户决定 |
| 消歧结论不记录 | 下次同样的需求再问一遍 | 写入 catalog + conventions |

## 检查清单

- [ ] 读过数据源（**量级**、结构、有无层级、可否自造），不是只听描述
- [ ] 读过项目已有同类场景
- [ ] 提问用的是数据特征，不是形态名罗列
- [ ] 排除了哪些方案，以及排除理由
- [ ] 复述结论时说明了依据，用户不需要懂组件也能判断对错
- [ ] 消歧结论写入了 catalog 与 decisions 日志
- [ ] 记录写的是通用形态描述，不是组件名
