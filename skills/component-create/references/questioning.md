# 提问：从模糊描述定位到具体形态

> 提问的作用是**选定**组件（单选下拉还是多选下拉），**不是**用来描述组件。组件的完整说明来自它那份**预设提示词**（`preset/` 下一个组件一份）。

## 描述是素材，问题是产物

```
预设提示词里某个参数存在
  → 该维度有分支
  → 不问清可能选错分支
  → 生成一个问题
```

例：选择类有「选择模式」「是否可搜索」「数量上限」三个维度
→ 对应「要不要多选」「要不要能搜」「最多选几个」三个问题。

**每条问题要带「为什么」**，可直接转述给用户——用户不懂组件，但懂「多选没上限会把控件撑爆」。

## 问数据，不问形态名

用户只会说视觉形态（「下拉选择框」），不会说组件名。指哪一种形态，取决于**他的数据**。

```
✗ 「你要哪种下拉？简单 / 可搜索 / 多选 / 标签 / 级联 / 树形 / 按钮组 / 分段 / 穿梭框」
✓ 「数据有层级关系吗？」→ 无 →「大概多少条？」→「需要同时选多个吗？」
```

几个数据特征问题就能把候选砍到一种。**用户不懂「级联」，但一定知道数据有没有层级。**

## 先读，再问

```
1 读数据源     多少条？有层级？可否自造？     ← 最强信号，多数情况到此截止
2 读已有组件   项目里同类场景怎么做的？
3 二分提问     问数据特征，一次一个
4 明确询问     前三者都定不了且选错会返工
```

## 追问按使用流程排序

```
用户看到 → 加载/空/错误 → 选择或输入 → 确认提交 → 取消返回 → 边界权限 → 变体与场景
```

人先想「用在哪」，再想「喂它什么」，最后才想「长什么样」。反过来先问圆角，用户答得随意——因为还不知道组件要干什么。

## 能推断的绝不问

```
1 能从项目代码读出来？      → 读代码，不问
2 能从既有约定推出来？      → 用约定，不问
3 不明确会返工或架构错误？  → 才是必须问的
```

推断出的默认值**要显式告知**，别让用户以为是自己选的：

> 已按项目现有 <某组件> 的做法自动设定：圆角取样式源里的默认、主色取 `--brand-primary`。不同的话告诉我。

## 硬上限

- 单轮 ≤3 题
- **总轮次 ≤2 轮**

超限说明推断做得不够，应回退去读代码，而不是把负担转给用户。提问用**预设选项**，不用开放式问句。

## 用户已指定组件形态时

仍要检查边界——指定的人常常只知道名字，不知道它做不到什么：

> 用下拉做多选没问题，但选了 30 项时 30 个标签会撑爆控件。建议设上限收纳，或改用穿梭框。

**说清代价让用户决定**，不要只说「不建议」。

## 平台

需求为 **PC 优先，但移动端要一起设计进去**：涉及弹层 / 选择 / 触摸的组件，追问时把移动端形态一并确定（如弹层用底部弹层还是全屏）。
