# 八步追问脚本与 Gate 机制

## 为什么是八步

提问顺序严格对齐**用户使用组件的生命周期**，而不是代码结构：

```
用户看到组件 → 加载/空/错误 → 选择或输入 → 确认/提交 → 取消/返回 → 边界与权限 → 变体与其他场景
     ①              ⑥              ③            ④          ⑦            ⑥          ⑤
```

人先想「用在哪」，再想「喂给它什么」，再想「怎么选」，最后才想「长什么样」。按这个顺序问，用户的思考是顺的；反过来先问圆角和配色，用户答得很随意，因为还不知道组件要干什么。

## 三级 Gate

每个待定项先过 Gate 判定，绝大部分问题在这一步就被消灭了。

| Gate | 判据 | 处理 |
|---|---|---|
| **G0 阻断项** | 不明确会直接导致返工或架构错误 | 必须问，选项化 |
| **G1 可推断** | 能从代码、已有组件、设计系统推断 | **不问**，直接定默认值并标注「已自动设定」 |
| **G2 偏好项** | 主观审美、可后续调整、不影响架构 | 合并成一次提问 |

### G1 的推断来源（按优先级）

1. 项目已有同类组件的实现方式 ← 最强信号
2. `.ui-kit/conventions.md` 的既有约定
3. `.ui-kit/tokens.json` 的令牌默认值
4. 组件库自身的设计惯例（如 antd 的 `size` 三档）
5. 组件所属场景的通行做法

**推断出的默认值必须显式告知**，不能让用户以为是自己选的：

> 已按项目现有 `<已有组件>` 的做法自动设定：圆角 6px、主色取 tokens.primary。不同的话告诉我。

这既是尊重，也让用户有机会低成本纠正。

### G2 的合并原则

G2 全部合并成**一次** `AskUserQuestion`，不超过 3 题。不要在一个组件上开三轮问卷。

## 八步详解

每步标注了：是否 G0、问题原文、预设选项、默认值、以及**影响什么**。

### ① 场景定位

**Gate：G0**（不问会导致组件职责错位，是最常见的返工原因）

问：这个组件用在哪、承担什么职责？

选项：
- 页面主操作区（表单提交、创建/编辑）
- 筛选与查询区
- 数据展示（列表、详情、图表）
- 反馈与提示（确认、错误、空状态）
- 布局容器（分栏、折叠、分隔）
- 导航（菜单、标签页、面包屑）

**影响**：决定组件的尺寸层级与视觉权重（主操作区用主按钮，筛选区用紧凑态）、决定是否需要权限控制、决定在页面中的位置约定。

> 追问要点：同一角色在不同产品里形态差别很大。筛选区的 Select 通常是小尺寸带搜索，不该用大尺寸。

### ② 数据契约

**Gate：G0**（数据规模直接决定要不要虚拟滚动、要不要远程搜索）

问：数据从哪来、多大规模？

选项：
- 静态枚举（写死在代码里，< 20 项）
- 接口返回，一次性全量（< 200 项）
- 接口返回，需要分页/懒加载
- 远程搜索（输入即请求，需防抖）
- 树形/层级数据
- 关联数据（需多组件联动）

**影响**：> 100 项必须考虑虚拟滚动；远程搜索需要防抖 + 请求时序控制 + loading 态；层级数据优先 Cascader/TreeSelect 而非 Select 自行拼装。

> 追问要点：数据里有没有「已选但选项被删」的孤儿值？这决定要不要 `labelRender` 兜底。

### ③ 选择 / 输入模型

**Gate：G0，但多数情况在形态消歧阶段已确定（见 `morphology.md`）**

本步回答的是**已选定的组件内部**该怎么配，不是选哪个组件。「下拉选择框」到底指 9 种形态中的哪一种，在形态消歧阶段就定了；到这一步形态已锁定，不要重复问「你要哪种下拉」。

**只在以下情况回到本步追问**：

| 情况 | 追问什么 |
|---|---|
| 形态消歧时未完全确定 | 「数据有层级吗？」→ 决定级联/树形/单选 |
| 多选且无上限 | 「最多选几个？」→ 无上限会撑爆控件，需 `maxTagCount` 收纳 |
| 选择类但允许自造 | 「需要允许输入列表外的值吗？」→ 决定是否用 tags 模式 |

**影响**：自由输入与固定枚举是两个不同组件，不要用 Select + `mode="tags"` 硬凑 AutoComplete——前者会允许用户造出脏数据。

> 追问要点：多选上限是多少？无上限的话展示形态会崩（几十个 tag 把控件撑爆），需要 `maxTagCount` + 「更多」收纳。

### ④ 交互与校验

**Gate：G0**（影响表单整体一致性）

问：校验什么时候触发？

选项：
- 失焦即校验（onBlur）
- 输入中实时校验（输入即反馈）
- 提交时统一校验
- 不校验（仅筛选区等非提交场景）

**影响**：与项目整体表单策略必须一致。同一表单里一半失焦校验一半提交校验，体验是割裂的。

追问要点（若是提交校验）：
- 错误文案显示在哪（字段下方 / 右侧 / tooltip）？
- 第一个错误字段是否自动聚焦？

> 追问要点：破坏性操作要不要二次确认？删除单条 vs 批量删除的确认策略不同。

### ⑤ 形态规格

**Gate：G2**（审美偏好，一次问完）— 但**令牌值从 tokens.json 取，不问**

问：视觉形态偏好？

选项：
- 尺寸：大 / 中 / 小
- 形态：描边 / 填充 / 无边框 / 下划线
- 强调程度：主要 / 次要 / 文字

**不问的**：具体圆角、间距、色值、字号 —— 这些从 `tokens.json` 取。若令牌里缺项，说明需要补令牌，此时才问。

**影响**：影响控件高度与信息密度。同一页面混用三种尺寸会显得很乱。

> 注意：平台相关的形态约束从平台包取。移动端没有 hover 态，尺寸下限也不同。

### ⑥ 状态矩阵

**Gate：G1 为主，G0 视场景**

绝大多数状态是必选项，直接定，不问：
- default / hover / focus / active / disabled
- loading / error / empty

**需问的 G0 情况**：
- 加载超过 1 秒时，用户能否做别的事？→ 决定是局部 loading 还是全屏遮罩
- 无权限时，是隐藏入口还是禁用并提示原因？
- 空状态是首次为空还是筛选后为空？两者文案与引导不同

**影响**：状态是组件规格里最容易被漏的部分，也是使用体验差距最大的地方。规范库要求状态必须全枚举。

### ⑦ 覆盖与联动

**Gate：G0**（影响技术实现，直接导致 bug）

问：这个组件会出现在什么位置？

选项：
- 普通内容流
- 表格单元格内（空间极紧）
- 抽屉 / 弹窗内（可能被父级 overflow 裁剪）
- 固定表头 / 悬浮工具栏
- 容器内有独立滚动区

**影响**：
- 在 overflow 容器内 → 弹层需要 `getPopupContainer` 指定挂载节点，否则被裁剪
- 在表格单元格内 → 尺寸必须压缩，多选 tag 数量要限制
- 页面滚动时跟随 → 需要挂到 body 而非局部容器

> 追问要点：会不会出现多个同名弹层？需要 `open` 受控 + `onOpenChange` 管理显隐。

### ⑧ 交付形式

**Gate：G1**（按项目规范定，除非项目没有规范）

不问的：受控/非受控的选择、导出方式、测试要求 —— 这些在项目既有组件里有先例，照抄。

**需问的 G0 情况**：
- 组件需要被业务侧二次封装吗？→ 影响是否要暴露组合式 API（headless 模式）
- 需要支持服务端渲染吗？→ 影响是否依赖浏览器 API

**影响**：决定组件 API 的开放程度。过早开放会锁死设计，过晚开放会导致业务侧复制粘贴。

## 提问纪律（硬约束）

1. **单轮 ≤3 题**，用 `AskUserQuestion` 提供 2-4 个预设选项，UI 自动提供自由输入兜底
2. **每题必须标注影响**（「影响：是否需要虚拟滚动」），让用户知道为什么问
3. **轮次上限 2 轮**。超限说明推断做得不够 —— 应该回退读代码和 registry，而不是把负担转嫁给用户
4. **先复述理解再生成**。八步答完后整理成一段话确认，避免理解偏差浪费一个完整组件
5. **不追问已明确的**。用户开头的描述里已经交代的，不要再问一遍
6. **能从代码读出来的绝不问**。用户的耐心比我们的完备性更值钱

## 追问的替代方案

有些「问题」根本不需要问用户，用下面的方式解决：

| 看似需要问 | 实际解法 |
|---|---|
| 「圆角用多少？」 | 读 `tokens.json` |
| 「这个项目用什么 UI 库？」 | 读 `package.json` |
| 「列表页的筛选一般怎么做？」 | 读 `conventions.md` |
| 「项目有类似组件吗？」 | 跑 `scan_components.py` |
| 「用户会不会用到 500 条数据？」 | 从数据来源代码与已有列表页实现推断 |
| 「组件要支持键盘吗？」 | 不需要问，规范库要求必须支持 |
