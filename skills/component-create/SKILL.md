# component-create — 组件创建

## 职责边界

**管「这次怎么做」，不管「应该怎么做」。**

| 属于本包 | 不属于本包 |
|---|---|
| 形态消歧（用户说「下拉选择框」到底是哪种） | 制定交互规范 |
| 复用 / 扩展 / 新建的决策 | 定义设计令牌 |
| 逐个组件的追问 | 批量巡检存量组件 |
| 按七维契约描述并生成组件 | 决定项目该用哪个组件库 |
| 填写组件规格文档 | 平台 hover/触控热区等差异规范 |

**要定规范或审查存量 → 用 `component-governance`。**

## 前置：加载项目规范

本包**不自带规范**，规范来自项目的 `.ui-kit/` 产出物。

```bash
ls .ui-kit/tokens.json .ui-kit/conventions.md 2>/dev/null
```

**若 `.ui-kit/` 不存在**：项目还没接入治理。此时应：

1. 明确告知用户「本项目尚未建立组件规范，本次生成仅为通用实践建议」
2. 仍按本包流程走完，但所有设计值标注「建议值，需治理确认」
3. 提示用户后续用 `component-governance` 初始化

**若存在**，按需读取（不要一次全读）：

| 读什么 | 何时读 |
|---|---|
| `.ui-kit/tokens.json` | 生成前必读（所有尺寸/圆角/间距/色值从这取） |
| `.ui-kit/conventions.md` | 追问前读（已知约定不问用户） |
| `.ui-kit/registry.json` | 复用决策前读 |
| `governance 的七维契约` | 生成前读（怎么把组件描述清楚） |
| `governance 的交互规范` | 生成前读（Do & Don't） |
| `governance 的平台差异` | 涉及 hover/拖拽/点击目标时读 |

**读不到治理包时**：仍按七维契约的通用要求生成，但**明确告知规范未加载**，且不凭印象编造具体规范条目。

### 跨包调用：定位治理包

步骤 5 的校验脚本在治理包里。Skill 之间没有 import 机制，需**先定位再调用**：

```
1. 取本 SKILL.md 所在目录的绝对路径
2. 向上找到包含本包的 skills/ 目录
3. 在同级查找 component-governance/
4. 找到 → 用其中的 scripts/ 与 references/
   找不到 → 在可用 Skill 列表中搜 component-governance
             仍找不到 → 跳过脚本校验，改为人工逐条对照，
                       并明确告知「治理包不可用，未做机器校验」
```

治理包版本（`contract_version`）与本包不一致时**停止并告知用户** —— 版本错配会导致规范与校验脚本对不上。

## 主流程

```
1. 形态消歧       用户说形态词时，确定要哪种形态   ★
      ↓
2. 复用决策       查 registry → 复用 / 扩展 / 新建
      ↓
3. 追问细节       形态定后，确认具体配置（1-2 轮）
      ↓
4. 按契约生成     七维描述 + 代码 + 规格文档
      ↓
5. 校验           硬校验（脚本）+ 软校验（逐条对照规范）
      ↓
6. 沉淀           写 catalog + 回写 tokens / conventions
```

**顺序不可颠倒**：形态没定就问「圆角用多少」是浪费——组件可能根本不需要弹层。

## 步骤 1：形态消歧 ★

**用户几乎不会说组件名，只会说视觉形态。**「下拉选择框」里，「选择」在业界至少有 9 种形态（简单选择 / 可搜索选择 / 多选 / 标签输入 / 级联 / 树形 / 按钮组 / 分段 / 穿梭框），指哪一种取决于他要解决什么问题，**不取决于他说的这个词**。

**不消歧的代价是静默的**：需求是「从 500 个商品里搜一个」，做成简单下拉框——组件层面完全符合要求，体验层面是灾难。**不报错、评审看不出来，用户立刻感受到。**

消歧顺序：

```
1. 读数据源   → 结构？多少条？有层级？可否自造？   ← 最强信号，多数情况到此为止
2. 读已有代码 → 项目里同类场景怎么做的？（registry.json）
3. 二分提问   → 问数据特征，一次问一个
4. 明确询问   → 前三者都定不了且选错会返工
```

**二分优于罗列**：

```
✗ 「你要哪种下拉？简单选择/可搜索/多选/标签输入/级联/树形/按钮组/分段/穿梭框」
   → 用户不懂这些术语，等于把问题原样退回

✓ 「数据有层级关系吗？」有 → 级联或树形；无 →「大概多少条？」→「需要同时选多个吗？」
```

三个数据特征问题能把 9 种形态砍到 1 种。**用户不需要懂组件，只需要描述自己的数据。**

**判定表见 `references/morphology.md`** —— 是「形态 ↔ 数据条件」的映射，不绑定任何组件库。

**用户指定了组件时也要检查边界** —— 指定的人常常只知道名字，不知道它做不到什么：

> 用下拉做多选没问题，但选了 30 项时 30 个标签会撑爆控件。建议设上限收纳，或改用穿梭框。

**说清代价，让用户决定**，不要只说「不建议」。

## 步骤 2：复用决策

1. 读 `.ui-kit/registry.json`
2. 校验指纹覆盖率。失配则请治理包跑 `scan_components.py` 增量重扫
3. 需要时查项目所用组件库的官方文档 —— **确认能力边界，不假设某个组件一定存在**

| 结论 | 判据 | 动作 |
|---|---|---|
| **复用** | 已有组件能力完全覆盖 | 直接用，输出组件名与理由，**不创建** |
| **扩展** | 已有组件能力接近，加 variant/props 即可覆盖 | 扩展已有组件，**优先于新建** |
| **用库** | 组件库能直接配置解决 | 用组件库 + 配置，**不写新组件** |
| **新建** | 库组件需组合多个才能凑出 | 告知组合方案与代价，确认后再新建 |

**「用库」这一档最容易跳过，但它最省事。** 在讨论自建之前必须先确认。

选型时明确告知组合方案与代价（例：「级联能做，但需把扁平数据转成 treeData，联动场景下性能不如树选择」），不要只给结论。

**「新建」前必查**：新组件的变体轴与已有组件是否重合？重合高就该扩展，不该新建。

## 步骤 3：追问细节

**形态已定**。追问回答的是「这个组件怎么配」，不是「用哪个组件」。

完整方法论见 `references/questioning.md`。要点：

- 顺序固定八步：场景定位 → 数据契约 → 选择输入模型 → 交互与校验 → 形态规格 → 状态矩阵 → 覆盖与联动 → 交付形式
- 第 3 步「选择输入模型」多数情况在消歧阶段已定，**不要重复问**
- 平台相关项（hover、拖拽、点击目标）从治理包的平台规范取
- 每题必须标注「影响什么」
- 单轮 ≤3 题，用 `AskUserQuestion` 提供预设选项
- **轮次上限 2 轮**。超限说明推断不足，回退读代码和 registry，而不是把负担转嫁给用户

## 步骤 4：按契约生成

**生成前先复述理解** —— 把消歧结论 + 八步答案整理成一段话确认，避免理解偏差浪费一个完整组件。

然后按七维契约描述（详见治理包 `component-design.md`）：

```
1 角色      解决什么问题 + 不解决什么
2 数据契约  形状/量级/可否自造/变更频率
3 交互契约  含反悔与取消路径
4 状态全枚举 12 态，disabled ≠ readonly
5 边界与代价 「到 Y 程度会 Z」
6 变体轴    variant / size
7 无障碍    键盘 / 焦点 / 读屏
```

提示词骨架见 `references/component-prompts.md`（含选择类/输入类/反馈类/展示类等类型专用段）。

**取值纪律**：所有尺寸、圆角、间距、色值从 `.ui-kit/tokens.json` 取，**不写硬编码**。令牌缺项时：

1. 先看能否用已有值组合
2. 确实需要新增 → 告知用户，让治理包补进令牌
3. **不要在组件里定义局部常量绕过令牌**

技术栈适配见 `references/stack-react.md`（React 场景）。

## 步骤 5：校验

**硬校验**（脚本，客观）：

```bash
# 令牌一致性 + a11y 基础项
python3 <governance>/scripts/check_tokens.py <组件路径> --tokens .ui-kit/tokens.json --platform web

# 七维契约审查（含规格文档）
python3 <governance>/scripts/check_contract.py <组件路径> --spec-dir .ui-kit/catalog
```

**软校验**（逐条对照治理包的交互规范）：每条标记「满足 / 违反 / 不适用」。不适用要说明原因，不许静默跳过。

发现问题**当场修**，不要列一堆问题让用户自己改。

## 步骤 6：沉淀

**消歧结论必须落盘** —— 这是「下次免问」的关键。

```
消歧结论 ──→ catalog/<Component>.md 第 1 节   为什么是这个形态、依据是什么
问答答案 ──→ catalog/<Component>.md 其余节    完整七维规格
           ├─→ tokens.json（若有新数值）      需治理包同步 DESIGN.md
           └─→ conventions.md（若有新约定）    项目级约定
决策过程 ──→ logs/decisions.mdl               JSONL，可回溯
```

**记录写通用形态描述，不写组件名** —— 组件名会随换库/升级失效，「可搜索的单选选择」不会。

**晋升机制**：同类需求出现 2 次以上相同消歧结论（如「商品选择一律用可搜索单选」），写入 `conventions.md`，下次直接采用**不必重新消歧**。

涉及令牌变更或规范变更时，**提示用户调用 `component-governance`** —— 本包不该单方面改全局规范。

## 兜底

规范未加载或治理包缺失时，仍应做到：

1. **复用优先** —— 先找项目里已有的组件，不重复造
2. 追问不超 2 轮，聚焦会导致返工的阻断项
3. 按七维契约的通用要求描述组件
4. **明确告知「规范未加载，以下为通用实践建议」**
5. **不要凭印象编造**具体规范条目或组件库 API。不确定的标注「需确认」

## 常见反模式

| 反模式 | 问题 | 正确做法 |
|---|---|---|
| 直接找"下拉框"就开始写 | 500 条数据做成简单下拉 | 先读数据量级 |
| 罗列所有形态让用户选 | 用户不懂这些术语 | 问数据特征 |
| 形态没定就问「圆角用多少」 | 组件可能根本不需要弹层 | 顺序：先形态，后细节 |
| 因为用户指定了组件就跳过检查 | 指定的人常不知组件边界 | 说明代价让用户决定 |
| 在组件里硬编码色值尺寸 | 令牌体系被绕过就失效 | 从 tokens.json 取 |
| 一次问七八个问题 | 用户放弃 answering | 单轮 ≤3 题，上限 2 轮 |
| 消歧结论不记录 | 下次同样的需求再问一遍 | 写进 catalog |
| 自行修改全局规范 | 单方面改动影响其他项目 | 走 governance 流程 |
